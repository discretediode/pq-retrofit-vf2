Foundations

Why post-quantum, and why now

Today's public-key cryptography rests on two hard maths problems: factoring large numbers (RSA) and the discrete logarithm on elliptic curves (ECDH, X25519, ECDSA). A large quantum computer running Shor's algorithm solves both efficiently. That breaks every public-key algorithm in a normal TLS connection.

Symmetric cryptography (AES, SHA-2/3) is only weakened, by Grover's algorithm, which roughly halves the security level. AES-256 stays safe. That's why the retrofit only touches the public-key parts.

Harvest now, decrypt later

An attacker can record encrypted traffic today and decrypt it once a quantum computer exists. So the key exchange is urgent now: any data that must stay secret for years is already at risk. Authentication is less urgent: a forged signature only helps an attacker during a live connection, so it must be fixed before quantum computers arrive, but old recordings can't be attacked that way.

Why embedded devices matter

Industrial and IoT devices stay in the field for 10–20 years. A device shipped today will still be running when quantum attacks may be practical. Embedded CPUs are slow, so the worry is that PQC makes connections too slow. That's exactly what this project tests.

Say it

"Shor's algorithm breaks RSA and elliptic curves. Recorded traffic can be decrypted later, so the key exchange has to move to post-quantum now, and long-lived embedded devices have to move first."

Foundations

How a TLS 1.3 connection works

A TLS handshake does two separate jobs. Keep them apart in your head, because the project upgrades each one differently.

  1. Key exchange: both sides agree on a shared secret that nobody listening can work out. Legacy uses X25519 (elliptic-curve Diffie–Hellman).
  2. Authentication: the server proves it is the real server, by signing the handshake with the private key that belongs to its certificate. The hackathon server uses RSA-3072.
sequenceDiagram

    S->>C: ServerHello + key share (X25519 + ML-KEM ciphertext)
    Note over C,S: Shared secret known. Everything below is encrypted.
    S->>C: Certificate (ECDSA) + ML-DSA signature in extension 0xFE20
    S->>C: CertificateVerify (ECDSA signature over the handshake)
    S->>C: Finished
    Note over C: Core 1 checks ECDSA, core 2 checks ML-DSA, at the same time
    C->>S: Finished, then HTTP request
    S->>C: HTTP response

TLS 1.3 needs one round trip before the client can send data. That's why the internet round-trip time (about 25–35 ms to the hackathon server) dominates there, while on the local network (about 1 ms) the CPU time of the crypto dominates. That second case is the hardest test for PQC.

"TLS does two jobs: key exchange and authentication. I made both hybrid: ML-KEM with X25519 for the key, and ML-DSA with ECDSA for the server's identity."

Foundations

The algorithms, side by side

ML-KEM (FIPS 203, formerly CRYSTALS-Kyber) and ML-DSA (FIPS 204, formerly CRYSTALS-Dilithium) were standardised by NIST in August 2024. Both are lattice-based: their security rests on the Module Learning With Errors problem, solving noisy linear equations over polynomials, which no known quantum algorithm solves efficiently.

They work on polynomials with 256 coefficients, modulo a small prime: q = 3329 for ML-KEM and q = 8380417 for ML-DSA. The heavy work is polynomial multiplication via the NTT (a number-theoretic FFT) and generating matrices with SHAKE / Keccak hashing. That's why the SHA-3 speed-up from bit manipulation helped them so much.

KEM vs Diffie–Hellman

A KEM (key encapsulation mechanism) works differently from Diffie–Hellman. The client generates a key pair and sends the public key. The server encapsulates: it creates a random secret and locks it with that public key, sending back the ciphertext. The client decapsulates with its private key. Both now hold the same 32-byte secret. It still fits in one round trip, inside the normal key-share fields.

Why ML-DSA-44 and not ML-DSA-65

ML-DSA-44 is NIST security category 2, a match for P-256's roughly 128-bit classical strength. The IETF composite-signature draft pairs it with P-256 for the same reason. It's also smaller (2420 vs 3309 B) and verifies faster (1.0 vs 1.6 ms). Switching saved 1.6 ms.

Say it

"ML-KEM and ML-DSA are the NIST lattice standards from 2024. ML-KEM-768 is category 3, ML-DSA-44 is category 2, matched to P-256."

Foundations

Why hybrid instead of pure PQC

The new algorithms are young. If someone finds a classical attack on ML-KEM next year, a pure-PQC system would be broken today. Hybrid combines a classical and a post-quantum algorithm so that an attacker has to break both:

  • Hybrid key exchange (X25519MLKEM768): the two shared secrets are concatenated and fed into TLS's key schedule. The session key stays safe as long as either half holds. This is the same group Chrome, Firefox and Cloudflare already use by default.
  • Hybrid authentication (dual signature): the client accepts the server only if both the ECDSA and the ML-DSA signatures verify. A forger must break both.

Hybrid is also the transition path regulators recommend (for example Germany's BSI and France's ANSSI), and it keeps the classical algorithms that certifications still require.

Say it

"Hybrid means an attacker must break both the classical and the post-quantum part. If ML-KEM turns out weak, X25519 still protects us, and the reverse."

Your hardware

The StarFive VisionFive 2

  • SoC: StarFive JH7110, 4 × SiFive U74 cores, RV64GC, up to 1.5 GHz, Debian Linux.
  • No vector unit (no RVV), so no wide SIMD for the NTT. It does support the Zba and Zbb bit-manipulation extensions, which the default compiler settings don't use.
  • All 4 cores share one clock (one frequency policy). You can't run one core fast and the others slow.
  • Default clock policy: the ondemand governor, lowest step 312.5 MHz. It raises the clock only after it notices load.
  • Hailo-8L: an int8 neural-network accelerator over PCIe. It wasn't detected on the board, and the analysis says it wouldn't help anyway (see the questions).
  • Connected to the Mac by USB serial console and Ethernet. The board reaches the internet through the Mac.
Say it

"Four in-order RISC-V cores, no vector unit, one shared clock. So the tools I had were the clock policy, the compiler and the spare cores."

Your work

What you built

1. A modern TLS library on the board

Debian ships OpenSSL 3.0.9, which has no ML-KEM or ML-DSA. You built OpenSSL 3.5.9 (the long-term-support release with both algorithms built in) from source on the board, in a separate folder so the system library stays untouched. Three builds:

BuildChangeEffect
stdplain OpenSSL 3.5.9ECDSA verify slow (4.1 ms): generic C code on RISC-V
optenable-ec_nistp_64_gcc_128Fast, constant-time P-256 code: ECDSA verify 4.1 → 1.4 ms
bitmanipopt + -march=rv64gc_zba_zbbSHA-3 +50%, ML-KEM −13 to −19%, ML-DSA verify −15%

2. Hybrid key exchange

The client asks for the TLS group X25519MLKEM768. Against the hackathon server, its reply "handshake_method":"hybrid-pqc" confirmed it.

3. Hybrid authentication, two versions

FOCAL's hackathon server supports the hybrid key exchange, but its certificate is RSA-3072 only: re-tested on 12 Nov, it refuses ECDSA and ML-DSA signatures. So you wrote your own test server (on the Mac). It has an RSA certificate for legacy clients and an ECDSA certificate plus ML-DSA keys for hybrid clients. Both modes were measured against this same server, so the comparison is fair.

  • v1: after the handshake, the server signs a value unique to this connection (the TLS exporter) with ML-DSA and sends it with the first HTTP response. It works and needs no extra round trip, but the check can only start after the handshake, so it adds time.
  • v2 (final): the ML-DSA signature travels inside the Certificate message as a custom TLS extension (0xFE20). It signs a hash of the ClientHello and ServerHello, which contain both sides' random values and key shares, so it can't be replayed in another connection. Because it arrives together with the ECDSA signature, the board checks both at the same time on two cores.

4. Trust model

The client pins the server's certificate and ML-DSA public key, instead of trusting a public certificate authority. That's fine for a closed device fleet. For the open internet you'd use a PKI with post-quantum certificates (see Limits).

Security checks you ran

A wrong ML-DSA key is rejected. A missing ML-DSA signature is rejected. A wrong server certificate is rejected. The client never sends application data until both signatures have passed.

"I built OpenSSL 3.5 on the board. The key exchange is the standard X25519MLKEM768 group. For authentication I added an ML-DSA-44 signature next to ECDSA, inside the TLS handshake, bound to that exact connection, and both must pass."

Your evidence

How you measured

  • Baseline = the original legacy connection, X25519 + RSA-3072, at the board's default CPU setting.
  • 1000 connections per mode. Each comparison ran in 20 blocks of 50, alternating which mode goes first. Network changes or chip temperature then affect both modes equally.
  • Median as the headline number, because internet tails are huge (worst cases up to 524 ms from one network hiccup). The mean would be dragged around by a few outliers. Best, worst, p95 and mean are all in the reports too.
  • Paired blocks: in each block the two modes are compared directly. "Faster in 20/20 blocks" is very strong evidence. If there were no real difference, the chance of that is about 1 in a million. 17/20 corresponds to p ≈ 0.003.
  • Two scenarios: your own server on the local network (crypto dominates, the hard case) and the hackathon server over the internet (the network dominates, the realistic case).
  • Micro-benchmarks at a fixed 1.5 GHz. Under ondemand the clock changed between runs and timings varied 2×. That noisy file is kept and labelled unreliable.
  • Every run checked: the hybrid group was actually negotiated, and ML-DSA actually verified. 0 failures.
Watch out

The very first numbers (165 ms legacy vs 64–79 ms hybrid) were wrong: a local relay program added its own connection time to the legacy runs. If asked, say you caught it, fixed it, and that's why you switched to large, alternating, paired runs.

Say it

"1000 runs per mode, alternated in blocks so both modes saw the same conditions. I report medians and the number of blocks where one mode won."

Your solution

The three speed-ups, and why each works

At the default setting, hybrid was 27.95 ms vs 21.61 ms legacy (+29%) on your server, and +13% on the hackathon server. Each fix attacks a different cause.

Approach 1: Raise the minimum CPU clock (biggest win)

Problem: ondemand lets the CPU idle at 312.5 MHz and only speeds up after it notices load. A handshake is a 20 ms burst, so it's mostly over before the clock ramps up. The crypto runs at a fifth of full speed.

Fix: keep ondemand (still saves power) but raise scaling_min_freq to 750 MHz. One settings change, no code.

Why 750 MHz: you tested 750 and 1250 MHz minimums, the schedutil governor, and full speed. 750 MHz was as fast as 1250 MHz but cooler (+0.5 °C idle vs +1.9 °C). Fixed 1.5 GHz is fastest but runs about +6 °C hotter, which you saw heat the chip. schedutil at the default minimum was worse than the default.

Result alone: hybrid 27.84 → 16.19 ms (own server).

Approach 2: RISC-V bit-manipulation extensions

Problem: the U74 supports Zba and Zbb, but standard builds target plain RV64GC. Without them a 64-bit rotate takes three instructions (shift left, shift right, OR).

Fix: recompile OpenSSL with -march=rv64gc_zba_zbb. No code changes. The compiler uses single-instruction rotates (rol/ror), andn, and shifted adds (sh3add).

Why it helps PQC: Keccak (SHA-3/SHAKE) is mostly 64-bit rotations and AND-NOT. ML-KEM and ML-DSA spend much of their time in SHAKE. So SHA-3 got 50% faster and ML-KEM 13–19% faster. RSA, ECDSA and X25519 didn't change.

Result alone: hybrid 28.15 → 26.57 ms (−5.6%, 20/20 blocks). Small, but free.

Catch: the binary only runs on CPUs with Zba/Zbb.

Approach 3: Use a second core

Problem: hybrid authentication does two independent checks (ECDSA and ML-DSA), but normally one after another on one core while three cores sit idle.

Feasibility test first: a separate program timed each pair of classical and PQ operations, on one core vs two. The result was 1.5–1.65× faster, and client crypto went from 16.0 to 10.1 ms at the default clock. It uses a persistent worker thread, because creating a new thread per operation costs too much.

Into the real handshake: that's why v2 moved the ML-DSA signature into the Certificate message. When it arrives, a worker thread on core 2 verifies ML-DSA while OpenSSL verifies ECDSA on core 1.

Result alone: hybrid 28.19 → 24.57 ms (−12.8%, 20/20 blocks), no extra heat.

Why not 4 cores: there are only two independent checks. The rest of the handshake is a strict sequence (Amdahl's law).

Three facts judges may push on

  • Why hybrid gains more than legacy: the same fixes take hybrid down 48% but legacy only 27%. The fixes speed up client-side crypto, and hybrid does more of it.
  • Like for like, hybrid is even 1 ms faster than legacy on your server (both at COMBINED, 20/20 blocks). That's because the server's RSA-3072 signing (several ms) is slower than ECDSA + ML-DSA-44 signing.
  • On the hackathon server, like for like, hybrid is still +2.8 ms slower. The bigger ML-KEM messages cost a little on the internet, and hybrid authentication can't be used there. Your claim is about beating the baseline, which is what the task asks for.

Be upfront

Limits (say these before they ask)

  • Hybrid authentication only against your own server. FOCAL's server supports the hybrid key exchange, but its certificate is RSA-3072 only and it refuses ECDSA and ML-DSA signatures, so against it only the key exchange is hybrid. If FOCAL adds an ML-DSA certificate, OpenSSL 3.5 can use it directly.
  • The ML-DSA signature uses a custom TLS extension, not a standard. In production you'd use standard-track options: composite ML-DSA certificates (IETF LAMPS draft), pure ML-DSA certificates, or "Catalyst" certificates with an alternative key.
  • Pinned keys, not a PKI. That's fine for a closed device fleet, but a real rollout needs CA-issued post-quantum certificates.
  • The bitmanip build only runs on CPUs with Zba/Zbb.
  • The key exchange halves still run one after another inside OpenSSL. Parallelising them would need an OpenSSL patch (another 0.5–1 ms).
  • Energy wasn't measured.
  • The 750 MHz minimum isn't permanent yet. It needs a boot service, like the one used for full speed earlier.
  • Server is a Mac, not a second embedded device.
Say it

"The key exchange is fully standard. My authentication method is a working prototype; for production, I'd move it to composite ML-DSA certificates once the standard is final."

Glossary

PQC
Post-quantum cryptography: algorithms believed safe against quantum computers.
ML-KEM
Module-Lattice Key Encapsulation Mechanism, FIPS 203 (was Kyber). Agrees on a shared secret.
ML-DSA
Module-Lattice Digital Signature Algorithm, FIPS 204 (was Dilithium). Proves identity.
SLH-DSA
FIPS 205, hash-based signatures (was SPHINCS+). Very large signatures; not used here.
X25519
Elliptic-curve Diffie–Hellman on Curve25519. Classical key exchange.
X25519MLKEM768
The hybrid TLS group: both key shares are sent, and both secrets are combined.
ECDSA P-256
Elliptic-curve signatures on the NIST P-256 curve. Classical.
RSA-3072
Classical signatures; slow to sign, fast to verify.
Shor / Grover
Quantum algorithms: Shor breaks RSA and elliptic curves; Grover only weakens symmetric keys.
NTT
Number-theoretic transform, a fast way to multiply polynomials; the core of ML-KEM and ML-DSA.
Keccak / SHAKE
The SHA-3 family; ML-KEM and ML-DSA use it heavily.
Zba / Zbb
RISC-V bit-manipulation extensions: address arithmetic, and rotates / AND-NOT / bit counting.
ondemand
Linux CPU clock policy that raises the clock after it sees load.
scaling_min_freq
The lowest clock the policy is allowed to use.
Exporter
A TLS function that gives a secret value unique to one connection (used by hybrid auth v1).
Pinning
The client trusts one specific certificate or key instead of a certificate authority.
Median / p95
The middle value / the value 95% of runs are below.
RTT
Round-trip time on the network.
